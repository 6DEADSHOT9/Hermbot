# Phase 2 code review

Review scope: owner/bot authentication, configuration encryption, registry and supervisor ownership, transaction ordering, immutable execution receipts, clone state, attachment installation, lifecycle grants and approvals, native compatibility, and browser controls. Findings below were corrected before acceptance closure. Linux staging/HTTPS was explicitly deferred by the owner; subscription login and Phase 3 are outside this implementation.

| Finding | Correction | Verification |
|---|---|---|
| Attachment extraction could follow a bot-created workspace symlink. | Stage in a root-owned image directory; install with directory descriptors and `O_NOFOLLOW`, checksum verification and atomic replacement. | Symlink-directory/leaf regression test, native attachment read and clone proof. |
| Clone helpers initialized new data-volume roots with root ownership. | Set both target mount roots to the native Hermes user before copying selected state. | A real partial clone was recovered and its native runtime became healthy. |
| Raw SQLite copying could lose committed WAL data, and read-only source mounts could prevent creation of SQLite's WAL index. | Pause the source; copy database/WAL into isolated scratch storage; use SQLite backup into the target. | Workspace/history clone, native file verification, four-option browser clone and healthy native history startup. |
| Failed or ambiguously created clone helpers could prevent retry or hold deleted volumes. | Validate full ownership labels, resume created helpers, recreate settled failed helpers and remove owned helpers during deletion. | Same-operation recovery of the failed partial clone; confirmed deletion of acceptance volumes. |
| Provisioning reported success immediately after container creation, including a runtime that was failing to start. | Wait for Docker runtime health; preserve partial state and return actionable failure details. | The startup failure was reported honestly and recovered; all successful lifecycle evidence waits for healthy compatibility. |
| A restarting runtime could fail deletion because the stop check covered only `running`. | Stop both running and restarting containers before removal. | Restarting-container regression and recovery of the original failed delete operation. |
| Rebuilt image tags could reuse a container created from old image contents. | Include the resolved image identity in the configuration fingerprint. | Retained bots upgraded through owner actions while preserving their original volumes. |
| A lost provisioning receipt could repeat a completed lifecycle effect after supervisor recovery. | Persist payload hashes/results atomically on a dedicated supervisor volume, fsync file/directory, replay receipts, and clean clone helpers on replay. | Receipt replay rejects changed payloads; ambiguous transport reconciles the same operation ID. |
| Approved creation retry incorrectly spent or checked a second creation budget; a settled manager could reuse old authority. | Recheck live authority without consuming another creation, reject settled manager operations and stale/source-busy retries. | Approved failed-create retry and settled-parent rejection tests; partial-clone live recovery. |
| Provider/timezone changes could unarchive a bot, and saved timezone changes were not applied to runtimes. | Freeze prior status/desired state in the outbox; preserve archive on configure; queue between-run timezone configuration. | Archive-preservation and timezone/busy-work regression tests. |
| A renamed provider could be reimported from `.env` after restart. | Record the initial environment import and preserve owner-edited profiles. | Bootstrap-after-rename regression. |
| Pending work could be admitted while lifecycle configuration was taking effect; some lock orders could form cycles. | Fence task/delegation admission with a shared bot lock using `NOWAIT`; use workspace-before-source order for clone, root-before-grant for revocation, and nonblocking target locks for exact lifecycle approval. | Concurrent admission regression, original worker/grant tests and live collaborative regressions. |
| A duplicate task request could fail after its bot was subsequently stopped. | Resolve the original immutable task receipt before checking admission for new work. | Duplicate receipt after runtime-stop regression. |
| Group membership edits could remove a teammate with uncertain execution; approved specialist creation could exceed the group cap. | Block removal while native work is unresolved and check the six-member limit at approval. | Uncertain-membership and full-group specialist-approval regressions. |
| Readiness from a prior configuration could appear current during provisioning. | Clear readiness when queuing lifecycle changes and wait for the applied revision in browser acceptance. | Edit/archive/restore browser sequence and readiness-clear regression. |
| Settings forms submitted database-only fields, and some browser state survived retired bots, pagination, session expiry or changed conversations. | Send explicit settings fields; guard repeated settings submissions; recover active conversations and expired login; scope uploads to their original conversation; reset pagination and streamed text between runs. | Browser settings save/lifecycle controls, mobile reconnect and frontend compilation. |
| Deleting a bot hid its retained direct chat, and state windows could hide old unsettled work or conversation outputs. | Add read-only past-teammate navigation, preserve unresolved work in the state projection, and load all outputs for the selected conversation. | Retired-history browser acceptance and regression tests beyond the recent task/artifact windows. |
| The pinned native skills route passed unsupported `include_editorial`; skill enumeration's `skip_disabled` semantics were counterintuitive, and brand-new profiles had not yet seeded bundled skill files. | Apply a guarded pinned-source compatibility fix; include disabled skills in the owner catalog; run native idempotent skill synchronization before validation and enablement. | Runtime catalog enumeration and native selected-skill acceptance. |

Final verification passed: 51 backend tests, Ruff, TypeScript/production compilation, real-model lifecycle and collaboration acceptance, browser lifecycle/work/history controls, fresh desktop/mobile sessions, and active native execution surviving worker restart. The read-only completion audit confirmed five healthy runtimes with 15 isolated volumes and no pending operations or unsettled work.

The required local Phase 2 behavior is verified by the evidence matrix in [PHASE2.md](PHASE2.md). Existing planning archives were preserved and no Phase 3 milestone was started.
