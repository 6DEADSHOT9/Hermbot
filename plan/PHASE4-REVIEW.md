**Must fix:**

1. **The stock read verifier rejects valid receipt hashes — C36.**
   - **What this is:** `tests/phase4_read_acceptance.py:verify_reads` correlates native calls with durable backend receipts.
   - **Problem:** It hashes the full validated model, while `backend/service.py:tool_action` deliberately omits empty optional fields. The saved orchestration's stock `--verify` command fails; a new native read demonstrates the same mismatch. Synthetic verifier tests construct their hashes with the same incorrect full-model recipe, so the passing unit suite did not catch this integration gap.
   - **Fix:** Reuse the exact receipt argument canonicalization in the verifier and add a regression using an actual backend-generated receipt. Preserve stored hashes and the existing rejection checks. **Deferred until baseline evaluations under the owner's instruction.**
   - **If we skip it:** Required acceptance cannot be reproduced with the documented stock command. Independent correlation proves the receipts' integrity but does not turn that failing command into a pass; do not close Phase 4/final review yet.

**Should fix after baseline evaluations:**

2. **GitHub access failures hide the actual reason and disable valid reads — C37.**
   - **What this is:** The connector transport classifies rejected credentials/scopes and the dispatcher marks a connection for reconnect.
   - **Problem:** Both 401 and 403 become the same exception without the status/reason. The first issue creation was rejected while the saved token still authenticated and read the selected repository/issues. Exact original rejection details are unavailable.
   - **Fix:** Classify bounded provider-specific scope/resource/rate-limit/authentication failures and retain a safe actionable reason; avoid broad reconnect for a verified action-specific denial. The real provider blocker itself recovered after owner-confirmed permission correction, private reconnect and a fresh exact approval; issue write and item readback now pass.
   - **If we skip it:** Owners can be sent through unnecessary reconnection and lose working reads while diagnosing one rejected action.

3. **Native runs can misplace review metadata or report advertised tools missing — C35/C39.**
   - **What this is:** The model selects tools and constructs outcome-bound action arguments.
   - **Problem:** Several acceptance runs placed outcome metadata at the wrong level; another reported a missing connector despite its post-preparation advertised schema and made no invocation. These are observed native-run failures, not proof that every ordinary controller-managed request has the same behavior.
   - **Fix:** Retain these traces as baseline cases, compare the unstructured review payload with the existing typed connector route, and require concrete admission evidence before missing-access claims. Typed connector preparation successfully produced the reviewed threaded reply; that prompted recovery does not establish general reliability.
   - **If we skip it:** Work can stop or request access unnecessarily even while the backend permits the required action.

4. **The supplied Gmail Message-ID did not survive delivery — C40.**
   - **What this is:** The adapter supplies an operation-derived Message-ID intended to help reconciliation.
   - **Problem:** A real parent-message read returned a different Gmail-generated header. Inferring the parent header from source blocked one reply preparation and cannot be the sole recovery/search assumption for a lost receipt.
   - **Fix:** Use actual provider IDs/headers and corroborating evidence. The successful reply fixture read the actual parent header and verified actual delivered reply content, thread, Subject, In-Reply-To and References. Keep missing-receipt operations uncertain without automatic replay.
   - **If we skip it:** Recovery can search for a header the provider did not retain or prepare a reply against an incorrect parent identifier.

Verdict: **fix 1 and rerun the documented verifier before marking Phase 4 complete.** Live private-provider acceptance and fixture cleanup pass; final review remains uncleared because the required verifier correction is deferred under the owner's evaluation-before-fixes instruction. C38's editable-reply coverage gap is closed by actual provider readback, not by weakening the checklist.
