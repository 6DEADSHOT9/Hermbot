# Phase 5.1 — Routines (local acceptance)

Implemented on October 20, 2026. This is the routines milestone, not completion of Phase 5. Event triggers, recurring manager grants, notifications and remote hosting remain later milestones.

Open **Routines** in the sidebar to create or edit a saved instruction. Choose a teammate and results conversation, a named timezone, a one-time, interval, daily, weekday, weekly or monthly schedule, and the results required for each run. Preview uses the same calendar calculation as admission. The form can select shared file versions, conversation attachments and enabled skills. It can bound active work time, permitted start delay and runs per UTC day. **Run now** works while a schedule is paused. Pause, resume and delete preserve run history. An explicit chat request can prepare an inactive draft; inspect and save it in Routines before it runs. Regular discussion does not become scheduled work.

Each active bot gets one supported Hermes `--no-agent` one-minute script job. The script sends only a scoped wake token and bot/generation to Hermbot. The database decides which routine is due and admits work through the existing work item, result, task, budget, skill, file and connector checks. It stores one immutable owner instruction per saved revision and a distinct thread and native session for each occurrence. The native timer cannot submit new instructions, create a work item, or grant external access. The adapter, script and private plugin sit beside the pinned Hermes runtime; upstream source is unchanged.

An occurrence key is unique per routine/revision/time. At most one unfinished run starts; active attempts, revisions, pending reviews and unresolved connector effects block overlap. Queued runs are cancelled when their saved revision is edited or scheduling is paused/archived. Started work continues until the ordinary Stop action. Each scheduled run has a start window; missed runs are skipped by default. The optional latest policy admits only the newest occurrence within that window after downtime. A daily cap and an active work budget bound consumption. Three consecutive definite task failures pause future scheduling with an error visible in the routine list. Skipped and failed runs remain in history. An archived destination pauses its routines and requires explicit resume after restoration.

The optional **since last successful run** information window supplies frozen half-open source-data timestamps. It moves forward only after a completed task with verified required outcomes and no unresolved connector effects. Changing instructions, required results or selected inputs resets the cursor. It is context for the bot, not source-item deduplication or an external-action grant. Each connected-app action still uses the existing owner request, connection permission, workspace policy, exact review where needed, and operation receipt. Native independently authenticated browser/terminal actions retain their existing coverage limit.

Local proof: [two native scheduled runs](../test-results/phase5-routines-live.json) each completed with the required result; [the chat draft](../test-results/phase5-routines-draft-live.json) was created from one real owner message, stayed inactive and created no work item; [post-restart run](../test-results/phase5-routines-restart.json) used the same routine after worker/API recreation; [browser checks](../test-results/phase5-routines-browser.json) covered history, preview and desktop/phone widths; [source integrity](../test-results/phase5-routines-integrity.json) found all 2,169 upstream Python files unchanged in the image and three runtimes, with all nine private volumes preserved. [Backend results](../test-results/phase5-routines-backend.xml) and Ruff cover schedule edges, admission, authority, revisions, duplicates, outcomes, archive and failures. [Final local audit](../test-results/phase5-routines-final.json) confirms the fixture routines and group are archived, the timer is disabled, all work is settled and the fixture had zero connector operations. Their histories remain, including results visible from the archived-routine list on a phone ([browser proof](../test-results/phase5-routines-archived-browser.json)).

The computer and Docker must stay running and awake. This implementation uses the local owner workspace; there is no remote wake service. The routine list shows up to 200 definitions, prioritizing active ones; cursor pagination will be needed if this owner workspace approaches that count. Named-timezone daily schedules skip nonexistent daylight-saving times and use the first occurrence of a repeated hour. The information window does not guarantee that an external source will return unique items. Live acceptance used local arithmetic only; routine-initiated external writes were covered by isolated policy/receipt regressions, not a new provider mutation.
