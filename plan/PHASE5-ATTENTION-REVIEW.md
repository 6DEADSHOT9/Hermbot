# Phase 5.4 review and local evidence

What this change does: Hermbot now keeps durable owner attention for real questions, reviews, accepted results and recovery/setup problems. Browser push uses a separate encrypted delivery queue and explicit browser registration; reading an update cannot authorize or resolve work.

Reviewed against `/private/tmp/hermbot-phase54-before`, including connected callers of work projection, request eligibility, transport and logout. This workspace has no Git metadata. The assumed load is the existing single-owner local stack, three persistent bots, multiple browser tabs and concurrent API/background workers. This is a focused change review, not closure of the deferred historical issue backlog.

## Corrected findings

1. **The transport timeout became a captured default.** Adding a push-specific deadline initially bound `MAX_SECONDS` at function definition, breaking the existing slow-drip regression. Resolve the default at call time, keep original raw response callers unchanged, and expose response metadata only to the explicit push adapter. Network dispatch uses the pinned numeric address, original TLS hostname, no redirects/proxy inheritance and a bounded response. A DNS lookup that returns after its budget cannot proceed to network dispatch; the operating system controls resolver completion.

2. **A digest could notify for unrelated unread work.** The first summary eligibility query considered the whole inbox. Quiet/burst summaries now consider their actual covered delivery members, current versions and freshness. Overflow summaries intentionally represent fresh inbox backlog. Tests cover all original members resolving while another unrelated question remains unread, repeated processing and read-before-send.

3. **Quiet and preference changes could lose or repeat catch-up.** A repeated local hour could generate two different quiet-end identities, and policy changes could suppress a summary after its children had been covered. A local quiet-period identity survives the repeated hour; policy replacement retains fresh covered members and overflow-only obligations. The queue reserves one overflow position, keeps at most 1,000 fresh pending obligations per browser and counts recent dispatch attempts for the three-per-minute limit. The inbox itself is not dropped.

4. **Slow push delivery could delay attention.** Sequential projection and HTTP sending in the first worker loop could exceed the five-second attention target. Independent pumps in the same small service now project attention while a send waits. A regression blocks sending and verifies that a real database question still appears.

5. **Maintenance could acquire locks in the reverse order.** Delivery completion holds delivery before subscription; the first retention/reconciliation transaction held preferences/subscriptions before delivery. Retention now commits each record family independently. Server-key failure is projected into health from the subscription status rather than updating preferences while holding delivery locks. This was a review-discovered lock-order risk, not a claim of a reproduced production deadlock.

6. **Old or reclassified work could open incomplete detail.** The recent `/state` slice is insufficient for an old notification, and a cosmetic work association must not detach a recurring occurrence. The authenticated resolver reads exact source/work/thread identities; the bounded work reader has an explicit canonical-occurrence option. Published file links use that same identity. Task inspection falls back to the exact fetched task/children; navigation coordinates the conversation reset and thread. Regressions cover old targets and a running/completed occurrence whose display association is cleared.

7. **Endpoint identity did not fully describe registration replacement.** Re-registering the same endpoint with new browser keys now changes the generation. Revoked, expired and replaced registrations keep no usable encrypted credential; completion of an old generation cannot retire a newer one. Explicit logout disables only the current browser association, independently of normal session expiry. Endpoint/token keys remain encrypted and are omitted from all settings responses.

8. **Review errors could be hidden behind the inbox modal.** The reused review action originally put its failure only in the main conversation banner. Errors now reach the visible Attention panel as well. Exact review/answer handlers still make the final authorization and stale-state checks; push has no approval buttons.

9. **Dependent setup symptoms could become separate alerts.** A foreign-key link to a connection needing reconnection inhibits its source symptom; a known source-access/resync/inspection failure inhibits the dependent trigger symptom. Repairing the upstream condition can expose the still-unresolved downstream setup. No fuzzy cross-service correlation, shared admission or work ownership change was introduced.

Additional integration corrections: result evidence used an initially ambiguous SQL column and was simplified to the accepted requirement revision/output fingerprint; old pruned read records retain small tombstones without rehydrating details on replay. An overbroad artifact-reader edit also touched an unrelated revision reader and was corrected before deployment. The acceptance driver confused the task's numeric `attempts` with its `executions` collection, and later used a now-empty pending-question list after the real answer; both driver errors were corrected without creating replacement work or simulating an owner answer. The host frontend build lacks a Rollup optional native binary; the pinned container build and TypeScript check pass.
