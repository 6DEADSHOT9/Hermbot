## Implementation and practical limits

- Files are limited to 10 MB. UTF-8 text/Markdown/CSV/JSON/Python/JavaScript/HTML, PDF, PNG/JPEG/WebP, DOCX and XLSX are supported. Office previews extract bounded text rather than preserving page layout. Downloads retain original bytes. PDFs use the browser's built-in viewer. Preview text is capped at 200,000 characters; CSV previews at 201 rows and 30 columns; office decompression at 2 MB and 20 selected sheets.
- Uploaded workspace-library files stay owner-private until explicitly shared with a conversation. Task admission grants an exact immutable version. Revoking a conversation share prevents new admission; already admitted task copies/grants remain attached to their original work. Sharing a version does not automatically share later versions. Published conversation outputs carry task/bot provenance and form immutable named version families.
- Owner-managed custom skills use the `hermbot-` prefix. Bundled skills can be inspected and enabled; importing an editable copy preserves their originals. Memory/skill changes use native compare-and-swap, immutable history and a durable runtime refresh. Model improvement proposals require owner review. Cross-bot proposals require current management authority. Saving a successful workflow produces a disabled, owner-reviewed draft to generalize before enabling.
- Takeover has a persistent native viewer/epoch lease and a separate database admission fence. It blocks new dispatch and later native tools, waits for a foreground in-flight tool, and makes input ready only for the current viewer/epoch. Closing the pane, losing the WebSocket or recreating a browser session never hands back automatically. Another owner session must explicitly reclaim or force handback.
- This is a trusted single-owner local tool-admission boundary. It does not freeze arbitrary background processes a bot launched earlier or provide hostile-code OS isolation. Per-bot containers, networks and separate data/workspace/browser volumes remain in place. Only the supervisor holds the Docker socket.
- Secure input is typed through the authenticated live screen connection and cleared from local UI state. Product messages, approvals and tool/task records receive metadata and a completion acknowledgment, never the entered input. The destination application receives the input normally. The acceptance proof used a fake canary on a local-only form and verified its absence from product records after completion.
- The actual desktop uses the pinned native Hermes Bot Desktop primitives, TigerVNC, Xfce, Chromium and cua-driver 0.34.0. The driver release is labeled beta upstream; both architecture binaries are pinned and SHA-256 verified. Hermes is pinned to revision `749220ef0007f8d87bd1531f1c24b0fe93816385` / base image digest `d4da4a40cd7a28aba983775d9fd31d94cbf153eeb0cb9e844d6d0f612b7c24db`; noVNC 1.7.0 and websockets 15.0.1 are locked. The runtime image is `hermbot-hermes:phase3`; historical app/test `phase1` names remain compatible.
- Checks report upstream Starlette/Botocore deprecation warnings and a nonblocking Vite bundle-size warning from the desktop client. There are no failing checks. Linux staging/HTTPS, subscription model adapters and Phase 4 connected-app integrations remain future work.
