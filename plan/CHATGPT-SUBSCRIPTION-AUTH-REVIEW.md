Per-connection caller rotation bounds inference to two concurrent requests, within the existing global three slots and bounded normal admission. The runtime credential identifies the bot, rather than cryptographically proving a particular native tool's purpose; native per-bot run limits and current execution admission remain part of the boundary.

## Implemented behavior

- Workspace settings → Providers supports a separate ChatGPT connection, system-browser consent, cancellation, status checking, account-specific model discovery, explicit model test, permitted models/default/name, usage settings, retry, disconnect and removal.
- The host broker owns OAuth and the encrypted SQLite vault. Its dedicated encryption key lives in macOS Keychain. The API receives a pairing verifier and safe account metadata; OpenAI access/refresh/ID tokens stay in the broker. No Codex CLI auth store is read or imported.
- OAuth uses the documented public-client authorization-code/PKCE flow, one-use state, nonce, exact IPv4 loopback callback, issued registration ID, signature/issuer/audience/time/subject validation and plan scope checks. Identity-only authorization does not enable inference.
- Concurrent callers share refresh ownership. Received rotations are saved before identity verification; an interrupted/uncertain exchange does not blindly replay an old refresh token. Disconnect and stale operations are fenced by authority versions. Vault key rotation preserves both decrypting keys until the replacement ciphertext is committed and verified.
- The API admits runtime inference through a separate opaque, revocable runtime/provider/model credential. Backend model jobs use explicit provider revision and authorization version. Account credentials never enter bot provisioning payloads or environments.
- Hermes uses an existing named custom Responses provider. Its built-in auxiliary task configurations explicitly use the same route/model, with configured fallback chains removed for this route. The primary conversation, compression, vision with an actual image input, and title-generation adapters passed a disposable native fixture.
- Intake and teaching use the shared subscription transport; structured Responses assessment is explicitly separate from the actual Decisions API. Existing API-key behavior is preserved. Subscription credentials cannot select Decisions mode.
- The bridge is authenticated, versioned, bounded and cancels interrupted requests without automatic replay. Slow consumers are cancelled individually. Disconnect/status retain capacity when inference requests fill the regular queue. A terminal completion is required; late failures remain failures.
- Quota blocking is distinct from account validity. It stops new requests and offers an explicit recheck; no guessed reset time, paid API fallback or different-account fallback. Teaching/intake errors provide safe recovery instructions rather than raw provider bodies.

The OpenAI example DevKit is a research reference; its code was not vendored. The integration uses original application code, the documented protocol and locked dependencies. Its noncommercial SDK license was explicitly considered during planning.

## Local setup and operation

For this installation the dedicated environment, private directory, Keychain item, user LaunchAgent and API pairing mount are prepared. The API reports `model_broker_online: true`. Normal Compose startup retains the connection through the non-secret `MODEL_BROKER_PAIRING_FILE` path saved in private `.env`; no extra Compose override is required.

For a new Mac installation, first configure the existing local application, then run:

```sh
uv venv --python 3.12 .model-broker-venv
uv pip sync --python .model-broker-venv/bin/python --require-hashes model_broker/requirements.lock
python3 scripts/model_broker_setup.py
docker compose up -d --no-deps api
```

The setup script preserves other environment values with an atomic private-file replacement. The host secret `pairing.key` stays private; the API mounts only `pairing.sha256`. Other services do not get that mount. An unconfigured installation mounts an unusable public placeholder and offers no broker authentication.

Open [Hermbot](http://localhost:8780) → Owner menu → Workspace settings → Providers → Add ChatGPT connection → Continue with ChatGPT. The owner chooses the account/workspace and authorizes plan usage in OpenAI's browser flow. Return to Hermbot, select an available model and click Test model. That action sends one small text-only request; it includes no owner recording or work context. Only a tested model can be assigned to a teammate. Use teammate settings to select the new provider/model; existing bot assignments are not silently replaced.

For manual foreground operation, stop the LaunchAgent first and run `.model-broker-venv/bin/python -I model_broker/launch.py`. A second broker refuses the singleton lock. `python3 scripts/model_broker_setup.py --uninstall` removes automatic startup without deleting saved registrations or tokens; disconnect accounts in Providers before removing access permanently.

For vault encryption-key rotation, first stop the user service using `launchctl bootout gui/$(id -u)/com.hermbot.model-broker`, then run `.model-broker-venv/bin/python -I model_broker/launch.py --rotate-vault-key`, and reinstall/start with `python3 scripts/model_broker_setup.py`. Failed key cleanup retains the decrypting keys; do not manually replace the Keychain item. Key loss or an unreadable vault fails closed. Existing Codex/ChatGPT login state outside Hermbot is untouched.

## Remaining acceptance and limits

Current owner-reported blocker (November 2): OpenAI's browser authorization page shows “Your organization hasn't enabled access for this app”. This is not successful consent or a verified inference connection. The selected account/workspace and its application policy have not yet been confirmed. [OpenAI's sign-in guidance](https://help.openai.com/en/articles/20001410-sign-in-with-chatgpt) directs organization-level application access to a global admin in Admin Console → External access; workspace admin rights alone are insufficient. Identity approval and plan-usage eligibility remain separate checks. [The integration quickstart](https://developers.openai.com/siwc/quickstart) limits plan usage to eligible Plus/Pro users in participating apps, with selected private clients. Do not infer that an admin toggle alone guarantees this private application's eligibility, or substitute another application's client identity.

1. Owner completes OpenAI consent and explicit model test; actual eligibility is determined by OpenAI. The official local flow does not establish entitlement for every private/business or hosted application, nor promise the exact legacy Codex CLI allowance counter.
2. With an authorized selected provider, verify a real no-effect native tool/result round trip and reviewed-image processing. Real provider failures, quota exhaustion and revoked grants were simulated rather than deliberately induced in the owner's account.
3. Explicitly select the tested provider/model for the intended teammate(s), then resume the saved Zenpad refinement if its evidence is still retained. Skill testing, owner verification and publication remain their existing separate acceptance steps. Phase 6.2 is not complete merely because authentication works.

The API remains trusted to authorize consumption for its assigned workspace. Runtime credentials provide per-runtime/provider/model isolation; a bot can use its permitted model within that scope. They are not a cryptographic proof of the purpose of every request or a hard per-tool cost ceiling. Shared account capacity is bounded by the broker's concurrency/queue controls and existing workspace execution policy; complex scheduling/fairness across many accounts is outside this local release.

macOS Keychain protects storage at rest and separates secrets from containers. It does not defeat a compromised host administrator or arbitrary trusted owner-UID code; the Python Keychain backend's shared-executable limitation is explicitly retained from the threat model. Stronger hostile-host isolation requires separately reviewed signed packaging/OS boundaries. Restore procedures require reconnecting accounts rather than blindly restoring old rotating tokens; there is no product backup-import workflow that can make stale token material current. Remote/team/Windows/Linux brokers, Claude auth and a Codex harness replacement are not implemented.
