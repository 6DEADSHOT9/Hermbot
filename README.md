# Hermbot

A private local workspace for persistent Hermes teammates. Scout, Quill and Sage are the initial team. Owner-managed teammates, settings and reviewed lifecycle proposals are joined by a versioned file library, native memory/skills, private bot computers and editable reviews. See [Phase 1 acceptance](plan/PHASE1.md), [Phase 2 acceptance](plan/PHASE2.md), [Phase 3 acceptance](plan/PHASE3.md), and the [approved roadmap](plan/README.md).

Phases 1–4 and Phase 5 milestones 5.1–5.3 are complete for the owner-approved local scope. The application runs on this machine at [localhost:8780](http://localhost:8780). Routine schedules, editable drafts and run history are available in **Routines**; [Phase 5.1 acceptance and limits](plan/PHASE5-ROUTINES.md) record the live checks. Event triggers are available under **Routines → Events**; [acceptance and limits](plan/PHASE5-EVENTS.md) record all five live providers, own-write suppression, review fixes and 547 passing backend tests. [Phase 5.3 recurring management](plan/PHASE5-ORCHESTRATION.md) passed local acceptance, including 581 tests, four native manager demonstrations, actual owner-answer continuation after restart and final fixture cleanup. Notifications, Linux staging and HTTPS remain later work. Phase 3 and Phase 4 review evidence remains in [PHASE3-REVIEW.md](plan/PHASE3-REVIEW.md) and [PHASE4.md](plan/PHASE4.md).

Engineering failures, chronological history, causes, fixes and remaining gaps are recorded in the [issue and learning register](plan/ISSUES.md). [Original-chat coverage](plan/CHAT-COVERAGE.md) maps every human turn in the three verified source transcripts. Historical phase acceptance does not imply that later reported defects are closed.

## Run locally

Docker Desktop or Docker Engine with Compose is required. Builds and checks run in pinned containers; host Node is unnecessary.

```sh
python3 scripts/configure.py
python3 scripts/upgrade_config.py
docker compose up -d --build
```

The configuration scripts preserve existing `.env` values and keep the file private with permissions `0600`. For the initial OpenAI-compatible provider, set:

```dotenv
MODEL_BASE_URL=https://your-provider.example/v1
MODEL_NAME=your-tool-capable-model-id
MODEL_API_KEY=your-provider-key
```

Use `host.docker.internal` when the provider runs on the host. The container's `localhost` points to that container. Local Codex subscription authentication is an additional provider option through a separate Mac credential broker; existing API-key providers remain supported. See [setup, security boundaries and real-account acceptance](plan/CHATGPT-SUBSCRIPTION-AUTH-REVIEW.md#direct-codex-connection). Hermes remains unchanged. Claude subscription authentication remains follow-up work.

Log in with `OWNER_TOKEN` from `.env`. Browser sessions use opaque, expiring, revocable HttpOnly/SameSite cookies. Provider keys are encrypted in PostgreSQL and are never returned to the browser. Keep `CONFIG_ENCRYPTION_KEY` with private backups: changing or losing it prevents decryption of saved provider and runtime credentials.

Manage provider keys, permitted models, the workspace default, timezone, tool permissions and resource limits in **Workspace settings**. Editing a provider or timezone updates affected runtimes only between runs; the API reports busy work that must first settle. Model or role changes on a bot can explicitly stop affected work before applying. `.env` seeds the initial provider; once edited in the UI, that profile retains the owner's configuration across restarts. Defaults apply to newly created bots; existing bots keep their chosen provider and model.

## Teammates and conversations

Use **Create teammate** above the roster, or **Workspace settings → Teammates**, to create, edit, clone, archive, restore, start, stop or delete a bot. Configure its name, role, avatar, model, tools, skills, memory and CPU limits. Provisioning is asynchronous and reports runtime health and failures. A stopped or provisioning bot cannot begin new work.

Click the **Your team**, **Past teammates** or **Groups** heading to collapse or expand that sidebar section. The browser remembers your choices; Past teammates starts collapsed. Search temporarily expands sections to reveal matching conversations. The lists share one scroll area, with File library and owner controls kept visible below it. On smaller screens, open Work and outputs from the chat header when needed; close it with the backdrop, close button or Escape.

Clones always receive independent identity tokens, API keys and volumes. Select memories, installed skill files, workspace files and native history explicitly. The source pauses while the copy runs; its state is preserved. SQLite history uses a consistent backup including committed WAL data. Browser-state volumes and known credential/configuration files are excluded. Cloning custom skills also requires selecting their installed skill files. Archive preserves private volumes; deletion requires typing the exact name and removes that bot's runtime and private data/workspace/browser volumes. Saved task records and published artifacts remain available in the read-only **Past teammates** conversations.

Send an outcome in a direct chat, or create a group and choose its first recipient. Groups support two to six teammates and membership editing. Attach up to ten supported files, each up to 10 MB. Attachments remain bound to their conversation, have checksums, and are installed into the recipient's private workspace without following symlinks. Reply threads use separate native sessions. Reactions and participant mentions are available in the composer. Mentions identify conversation participants; the selected recipient owns the request and decides which permitted handoffs to make. Skill selection happens automatically for each assignment from the teammate's enabled procedures.

The work panel shows queued/running/review/waiting/completed state from actual runtime events. Inspect work to see native executions, consulted skills, missing-access explanations, teammate briefs, shared-input counts, dependencies, control delivery and lifecycle proposals. Edit instructions before execution starts; use Redirect for active work. Stop cancels the operation's descendants and waits for native executors to settle. Retry creates a new owner-requested operation after the old tree settles; uncertain execution blocks replay. Closing the browser leaves work running, and a fresh session recovers conversations and published outputs.

Artifacts are immutable files in MinIO with checksums, supporting text, code, PDF, Office documents and images up to 10 MB. Bots can publish a completed file directly from their permitted workspace; file bytes travel through the runtime adapter rather than model arguments. Bots exchange artifact IDs with explicit access grants and keep separate private histories and workspaces. The original proof clock schedules one native run between ten seconds and ten minutes ahead. Saved routines now provide recurring schedules with durable admission and explicit overlap rules.

## Routines

Open **Routines** in the sidebar to schedule a teammate for one-time or recurring work. Choose its conversation, instructions, expected results and timezone, then inspect the next occurrence preview before saving. Ask a teammate in chat to prepare an inactive draft if you prefer natural language; save it yourself to activate it. Run now, pause, resume, delete and history are available on each routine. Each occurrence has its own thread and work item. When the computer or Docker is asleep, missed starts follow the selected skip/latest policy. Connected-app actions still follow the workspace permission and review policy. See [Phase 5.1](plan/PHASE5-ROUTINES.md) for failure, overlap and restart behavior.

Enable **Coordinate teammates** in a routine or event trigger to select collaborators and an existing standing management permission, or create that permission inline. Each occurrence freezes this selected scope and shares its execution allowance across the manager and automated collaborators. Permission expiry pauses future starts. **Pause** affects future starts; **Pause and stop current run** also stops owned execution. Existing external-action reviews remain in effect. See [Phase 5.3 implementation, evidence and limits](plan/PHASE5-ORCHESTRATION.md).

## Management responsibility

Use **Edit group → Remove group** to remove a settled group from the sidebar. Saved task records and published files remain available; stop pending work before removal.

Ordinary messages use automatic conversation routing. Discussion, explanations, thanks and progress questions stay in the transcript. Concrete assignments create work items; revisions reference the same item while keeping execution trees and permissions separate. Users simply send a message. A shared intake process interprets it before execution, with current requirements and read-only access to earlier public conversation context. One message can include discussion and work changes. Failed interpretation preserves the message and offers Retry interpretation. If the meaning or target is unclear, it asks for clarification in chat. Work cards show assignments and published outputs, with finished work collapsed. **Remove from work list** and **Restore** change visibility without stopping or rerunning anything. Conversation responses have their own inspection/stop controls, and reviews or failures remain visible in the chat. Owner changes are recorded as work revisions regardless of the receiving bot. Durable commands deliver revisions to active or waiting assignments. Superseded requirements stop counting, and affected undispatched drafts are retired. Existing external receipts remain auditable; uncertain actions require reconciliation before repeating them.

New work records its required results separately from bot turns. The work card shows partial progress and whether it needs an answer, approval, access or reconciliation; a finished turn cannot erase an unfinished delivery. Ordinary questions have a text field or meaningful choices. Answer there or naturally in the conversation; the asking task receives the actual text. Actual owner answers are interpreted with the existing request. Application policy is separately identified and is never presented as something the owner said. Workspace settings includes Connected app actions: execute explicitly requested actions, or review each action. Account and resource permissions apply in both modes. Connector reviews show the destination and content with editable fields. A confirmed Slack member ID can be used for a DM draft without a pre-existing DM channel or history access. **Remove this requirement** drops an unneeded result explicitly; it differs from hiding the whole work card. Historical completed work is labeled as historical because required results were not recorded then. See [the implementation review](plan/WORK-OUTCOMES-REVIEW.md).

For new ordinary messages, Hermbot records required results during intake and binds assignments to them. Agents can use descriptive requirement keys when selecting handoff results or reporting progress. Preparation is optional capability discovery and skill consultation; operation access is checked when invoked. Historical execution paths remain compatible until the owner revises them. A finished bot turn cannot satisfy missing requirements. Automatic intake applies to `/api/v1/messages` with the default `auto` intent; explicit legacy intents and `/api/v1/tasks` retain their existing behavior for client compatibility.

Answering a bot's question preserves independent assignments and explicitly targeted work changes in the same message. Malformed context lookups and assignments missing required results receive correction feedback within the bounded intake loop. Exhausted interpretation reports its failure category, with sanitized diagnostic fields rather than private model replies; terminal subscription refresh failures require reconnecting in Providers. Regression coverage is in `tests/test_intake_recovery.py`.

New ordinary work separates teammate communication, required inputs and accepted results. `hermbot_message` queues a scoped inbox message without creating an assignment or blocking its sender. Busy teammates receive messages through supported request middleware; idle teammates can respond in an internal conversation execution. Replies reference the original message. `hermbot_delegate` creates a defined contribution or transfers responsibility for an entire named deliverable; it returns immediately. `hermbot_wait` names results or replies actually required before proceeding and releases execution capacity when the turn ends. A required contribution must settle and be submitted before dependent work can use it. Failed responses and assignments wake their responsible teammate. A settled unsuccessful contribution can be explicitly replaced with `replaces_task_id`, preserving its required status and history; running or uncertain effects cannot be replaced.

Publishing stores immutable evidence. The accountable assignment submits a final result with `hermbot_finish`, a recorded review, and references to required contributions it inspected. File contributions require an actual `hermbot_read_artifact` receipt before acceptance. Accepted results bind the requirement revision, artifact version/checksum and review; late or duplicate submissions cannot fulfill a revised requirement. Provider receipts remain recorded independently of final acceptance, and an artifact cannot prove external delivery. Research quality is assessed by the accountable agent; these checks enforce recorded requirements and evidence, rather than guaranteeing the truth of every research claim. Work cards show contribution submission/acceptance and required waits separately. Historical work retains its original semantics; active historical executions are not converted mid-run.

**Coordinate team** creates authority scoped to the selected teammates and this task tree. In **Workspace settings → Grants**, create a standing grant with a manager, target bots, allowed operations, expiry, creation budget and per-bot CPU/memory limits. Inspect and revoke grants there. Revocation stops every operation using that grant and leaves unrelated work running.

Managers can propose creating or configuring a bot and starting or stopping its runtime when the grant permits it. The owner reviews the exact configuration, prior state, resource implications and affected work. Allow once, deny, or edit the proposal; an edit creates a fresh approval and invalidates the old one. Changed configuration/provider revisions invalidate stale approvals. Approved operations enter a durable supervisor outbox; the manager resumes after provisioning settles, discovers the approved specialist and can incorporate it into the existing orchestration.

Deletion, provider credentials and access-policy changes remain owner-controlled. A denied proposal performs no lifecycle action. Provisioning failures preserve partial state and display a recovery action. Retrying a failed operation uses its original identity and approved payload. An ambiguous transport receipt remains in reconciliation, so it cannot silently become duplicate provisioning. A settled manager operation requires a new owner action rather than reuse of its old authorization.

## Runtime ownership and shutdown

Each bot has its own network, identity, native API credential and persistent data, workspace and browser volumes. Only the supervisor has Docker socket access. The API and worker attach to bot networks; database and storage stay on the control network. The only published application port is `127.0.0.1:8780`.

The supervisor owns dynamic `hermbot-bot-*` containers. Compose owns the API, worker, supervisor, PostgreSQL, MinIO and the runtime-image build helper. The old fixed runtime services are retained under the `legacy` profile for migration reference; do not start that profile alongside managed bots. Original Scout/Quill/Sage volumes are retained.

To stop the entire local application while preserving volumes, first let work settle or stop it in the UI, then run:

```sh
python3 scripts/stop.py
```

Restart with `docker compose up -d`. The worker reconnects API/worker network endpoints and starts only runtimes whose recorded desired state is running. Archived and explicitly stopped bots remain stopped. `docker compose stop` alone leaves supervisor-managed bot containers running. Avoid volume deletion for restarts. After changing the runtime image, apply a runtime start or configuration action to upgrade existing bots while preserving their volumes.

Hermes is pinned to revision `749220ef0007f8d87bd1531f1c24b0fe93816385`, base digest `sha256:d4da4a40cd7a28aba983775d9fd31d94cbf153eeb0cb9e844d6d0f612b7c24db`, with **no upstream source patches**. Request projection uses the existing `llm_request` plugin middleware; raw skill consultation uses `tool_execution` middleware; owner skill listing uses Hermbot's private runtime adapter. Runtime images have a read-only root filesystem and a root-owned managed plugin directory. The gateway runs as the Hermes user without effective Linux capabilities or privilege escalation; private state and workspaces remain writable. Python, Node, PostgreSQL, MinIO and Playwright are pinned; Python installation uses a hash-checked lock and the frontend uses `npm ci`. Rollup stays at `4.62.2` because `4.64.0` exhausted memory on this machine.

Hermes owns execution and native session history. PostgreSQL owns coordination, immutable receipts, leases, controls, approvals and rebuildable projections. Native dispatch retries retain their exact idempotency key within Hermes's retention period; missing receipts or ambiguous steering remain uncertain. Defaults are three concurrent executions, one active/uncertain attempt per bot, depth three and ten handoffs. New work has no automatic five-minute execution cutoff or twenty-minute deadline. It runs continuously until completion, a real wait, Stop, an explicit owner deadline, or its active work budget. The default budget is 60 combined active minutes across teammates and revisions in a work item; owner-input and approval waits do not consume it once observed. A budget pause preserves completed results and pending drafts; **Continue** adds another workspace allowance to the same work. It cannot continue a stopped task, an expired grant/deadline, or an unresolved external result. The earlier 24-turn runtime configuration has been replaced with a large supported native ceiling; the visible active budget governs practical execution. Ordinary continuations have no application execution-count cap; definite transient failures before any tool ran can recover at most twice. Worker restarts reconnect the existing run identity without replaying uncertain actions.

Configure active budgets and optional execution assessments in **Workspace settings**. Assessments run asynchronously and inspect progress metadata, repeated tool failures, current outcomes and budget. They never grant access, approve changes, increase budgets or declare completion. Guidance is opt-in; stale results, low confidence and provider outages leave healthy execution under its normal controls. Native Decisions uses a separately configured API provider's `/decisions` endpoint; the structured chat alternative uses `/chat/completions`. ChatGPT/Codex subscription sign-in does not establish documented Decisions access. Assessments are disabled until configured; no subscription login adapter is included in this change. Each assessment and its status is recorded in **Inspect work**. Explicit owner deadlines remain available as optional ISO timestamps through the task API; review expiry and management grants remain independent limits.

## Files, memory, skills and computer work

Open **File library** to upload supported documents, images, tables and code, import public HTTP links, search prior work, inspect provenance and immutable versions, share a selected version with a conversation, or download the original. New global uploads stay owner-only until explicitly shared or attached. Conversation shares apply to the selected version; an already admitted task retains its explicit grant and private copy when a share is revoked. Files are limited to 10 MB. Office documents have bounded text previews; PDFs use the browser's PDF viewer.

Open a teammate's **Memory & skills** from its chat header. Review and edit native personal notes or user memory, inspect bundled skills, import/create owner-managed `hermbot-` skills, enable selected skills, and load saved versions as new drafts. Empty memory removes its content; removing a custom skill disables it and removes its native file while retaining immutable version history. **Save as skill** starts an editable draft from completed work. Saves wait for idle native execution and refresh the runtime so later turns see the change. A bot can propose exact memory or skill improvements using `hermbot_review`; the owner can edit the content before approving it, and continuation waits for native application and runtime provisioning.

**Tools & application access** in that panel explains the teammate's current native tool availability and assigned connections. Agents can select up to three relevant enabled skills and consult them through `hermbot_prepare`, which returns raw instructions and optional capability checks. Empty selection is valid when no procedure fits. Required tools can be declared in skill frontmatter as `metadata.hermbot.required_tools: [read_file, hermbot_publish]`. Skills do not enable tools or expand permissions; their templates and inline commands are not evaluated during consultation. Current operation permissions are checked on use. Invalid references, missing permissions, authentication failures and unsupported operations have distinct recovery paths. Missing results remain visible in work inspection.

Managers discover effective teammate tools, enabled skills and application action names before delegating. A handoff can supply `expected_output`, explicitly granted `artifact_ids` and `attachment_ids`, and recipient skill requirements. Each recipient prepares independently. Private memory, browser sessions, credentials and arbitrary files are not copied. **Connections do not disable any owner-enabled native tools**, including terminal, browser and file editing. This applies to connected bots, their collaborators, revoked connections and historical task-tree restriction flags. Connector credentials remain in the backend; connector calls retain action/resource checks and exact approval or standing permission for changes. Independently authenticated browser sessions or terminal actions operate outside connector review coverage. Owner tool settings, work preparation, conversation routing and human takeover still apply. See the detailed [skills/tools plan](plan/SKILLS-TOOLS.md).

Open a teammate's **Computer** for its isolated desktop thumbnail or expanded live view. The desktop starts when a headed native browser needs it. Managed runtimes use Hermes's built-in browser tools; this pinned revision's `browser.backend: off` disables the optional Browser Use CLI replacement while retaining those tools. The default desktop memory floor is 1,024 MB; an existing explicit runtime setting is preserved. Take over to use the pointer and keyboard, then hand back explicitly. New dispatch pauses immediately, and input waits for an admitted tool to finish. The native control lease and epoch gate all bot tools and live input. Closing the pane, reloading or losing the connection retains human control. Another owner session can explicitly reclaim it; its new epoch disables the previous session's input. Browser profiles persist in separate per-bot volumes across recreation.

For secure input, focus the destination field on the bot's computer, then use the local password field to type through the authenticated live connection. The value clears immediately and does not enter a task payload, chat message, approval, event or API log. Submit through the computer, hand back, then acknowledge the input review. The destination website and browser retain their normal session state. This is a tool-admission boundary in a trusted single-owner runtime; it does not make arbitrary background processes started by native terminal commands an OS sandbox.

Editing an ordinary review or learning draft creates a new approval and makes the old one unusable. Lifecycle proposals retain their existing exact-change editor. Already-issued native command approvals must be denied and proposed again to change the command. Reviews can be denied or cancelled, and pending reviews expire with their task deadline.

Desktop startup requires 1,536 MB of free memory within that bot's container limit. If Computer reports insufficient memory, hand back control and let tasks settle, then edit the teammate's **Memory limit**. A 4,096 MB limit gives the desktop and browser more headroom than the default 2,048 MB; available host/Docker memory still matters. Scout was increased to 4,096 MB after this startup error, with its existing private volumes retained and desktop/thumbnail verified (`test-results/desktop-memory-fix.json`).

## Attention and browser notifications

Open **Attention** beside Routines for pending questions/reviews, unread accepted results and recovery/setup problems. Reading or dismissing an update never answers or approves work. **Mark visible read** applies only to the versions shown. Open an item to see its current work, exact decision, report, files or source setup; an old notification cannot approve a replaced or expired action.

Browser push is optional and starts off. Use **Owner → Notifications → Enable this browser**, grant the browser/OS permission, then **Send test notification**. OS text stays generic; authenticated details remain in Hermbot. Preferences include categories and quiet hours in an explicit IANA timezone. Work continues during quiet time, and questions keep their real expiry. Disable a browser there; signing out revokes the current browser association without revoking other browsers. Normal one-day session expiry does not revoke generic push.

For a fresh installation, privately generate stable keys once with `docker compose run --rm --no-deps -v "$PWD:/app" api python scripts/notification_setup.py --contact mailto:you@example.com`, then recreate `api` and `notification-worker`. Existing keys are preserved. `VAPID_PRIVATE_KEY` belongs only in the private environment; do not post it or a push endpoint in chat. The worker has no model/bot credentials and runs independently of agent execution.

Local desktop `http://localhost:8780` supports the secure browser APIs. Plain HTTP access through a phone's LAN address does not have the same exception. Real display depends on the browser, OS permission/Focus settings, internet access and the local machine/Docker staying awake. Push-service acceptance is not proof of display or reading.
